OneDesk · Microsoft 365 security

Hardening the Microsoft 365 mailbox connection

How OneDesk connects to your support mailbox, why it cannot read the rest of your organisation's mail, and the exact settings your Microsoft administrator should apply to keep it that way.

Audience Entra / Exchange admin Time ~30 minutes Delegated access only

Section 0“Doesn't this give the app access to every mailbox?”

This is the first question most security reviewers ask, and it is a fair one — it describes a genuine, well-documented weakness in a different way of building this integration. Here is the distinction, and how to verify which one you are looking at.

Two ways an app can reach Microsoft 365 mail

Microsoft offers two fundamentally different permission models. One is organisation-wide by default. The other is limited to a single sign-in. OneDesk uses the second.

The risky model

Application permissions

The app authenticates as itself (the “client credentials” flow) using permissions such as Mail.Read or Mail.ReadWrite.

Once an administrator consents, the app can read every mailbox in the organisation. Containing it requires a separate Exchange-side scoping policy that is easy to forget.

OneDesk does not use this.

What OneDesk uses

Delegated permissions

The app acts on behalf of one signed-in account, over standard IMAP and SMTP.

The resulting token can only open what that one account can already open. There is no organisation-wide reach to contain.

Blast radius: one mailbox.

Concretely, OneDesk requests exactly these three permissions and nothing else:

The complete scope OneDesk requests
https://outlook.office365.com/IMAP.AccessAsUser.All https://outlook.office365.com/SMTP.Send offline_access

It never requests any Microsoft Graph mail permission. If you see any of the following on the app, something is wrong — stop and raise it:

Mail.ReadMail.ReadWriteMail.SendMail.ReadBasic.All
i

Why “.All” appears in the permission nameThe scope IMAP.AccessAsUser.All reads alarmingly, but the .All refers to all folders within the mailboxes the signed-in user can already access — not all users. It is a delegated permission; it grants nothing on its own without someone signing in.

✓

The one-minute check that settles the argumentIn Entra, open App registrations ▸ your app ▸ API permissions and look at the Type column. Every row must read Delegated. If the word Application appears on any row, the concern above becomes valid for that permission and it should be removed. Screenshot this page for your security file.

The rest of this guide is about the risk that does remain in the delegated model: a delegated token inherits the reach of whoever signed in. So the whole job is making sure the account that signs in can reach nothing but the support mailbox — and that nobody else can sign in at all.

Section 1Create a dedicated support mailbox and service account

Two identities, each with one job. The shared mailbox holds the mail; a separate, deliberately powerless service account is the only thing that ever signs in to OneDesk.

  1. Create the shared mailbox

    In the Exchange admin center go to Recipients ▸ Mailboxes ▸ Add a shared mailbox and create the address support mail will arrive at, for example support@yourcompany.com.

    A shared mailbox needs no licence and has sign-in blocked by default — both of which are what you want.

  2. Create a dedicated service account

    Create one ordinary licensed user, for example helpdesk-svc@yourcompany.com. This account exists for one purpose: to be the identity that signs in at OneDesk's consent prompt. Nobody uses it for anything else.

    !

    This account's reach is OneDesk's reachIt must not be a Global Administrator or Exchange Administrator. It must not hold delegate or Full Access rights on any other mailbox. And it must not be a real person's account. Every one of those mistakes silently widens what the stored token can open.

  3. Grant it Full Access to that one mailbox

    Connect to Exchange Online PowerShell and run:

    Add-MailboxPermission -Identity support@yourcompany.com `
  -User helpdesk-svc@yourcompany.com `
  -AccessRights FullAccess -AutoMapping:$false

    This is the only mailbox permission the service account should ever hold. You can confirm what it holds with Get-MailboxPermission -User helpdesk-svc@yourcompany.com.

  4. Understand which address goes where

    OneDesk uses Microsoft's documented shared-mailbox pattern: it presents the shared mailbox address as the IMAP username while holding a token issued to the service account. That means the two addresses are not interchangeable on the OneDesk form:

    WhereWhich address
    OneDesk “Address” fieldsupport@yourcompany.com — the mailbox itself
    OneDesk “Username” fieldsupport@yourcompany.com — the shared mailbox again, not the service account
    Microsoft sign-in prompthelpdesk-svc@yourcompany.com — the delegate signing in

Section 2Enable IMAP and SMTP AUTH — on these mailboxes only

Modern Microsoft 365 tenants ship with these protocols switched off. Turn them on per mailbox, never across the tenant.

Set-CASMailbox -Identity support@yourcompany.com -ImapEnabled $true
Set-CASMailbox -Identity support@yourcompany.com -SmtpClientAuthenticationDisabled $false
Set-CASMailbox -Identity helpdesk-svc@yourcompany.com -ImapEnabled $true
!

Leave the tenant-wide switch aloneDo not run Set-TransportConfig -SmtpClientAuthenticationDisabled $false. The tenant-level block should stay in place; the per-mailbox settings above override it for just these two mailboxes. Turning it off tenant-wide re-opens SMTP submission for every account you have.

i

Two Microsoft deadlines your reviewer may ask aboutBasic authentication: Microsoft disables Basic auth for SMTP submission by default at the end of December 2026. This does not affect you — OneDesk authenticates with OAuth, which is the supported path. Legacy TLS: from July 2026 Microsoft refuses IMAP and POP connections using TLS 1.0 or 1.1. OneDesk negotiates TLS 1.2 or higher, so no action is required.

Section 3Register the app with least privilege

One app registration, in your own tenant, with delegated permissions only.

  1. Create the registration

    Go to entra.microsoft.com and open Applications ▸ App registrations ▸ + New registration. Name it something recognisable, e.g. OneDesk – Support Mailbox.

  2. Restrict it to your organisation

    Under Supported account types choose “Accounts in this organizational directory only (Single tenant)”.

    ✓

    One click, meaningful protectionThis alone makes the app unusable from any other Microsoft tenant. Even if the client ID and secret leaked, no account outside your directory could sign in against it.

  3. Add the redirect URI

    Open Manage ▸ Authentication ▸ + Add a platform ▸ Web and paste the callback address. It is specific to your organisation — copy the exact value OneDesk displays on the mailbox settings screen rather than typing it. It has this shape:

    Redirect URI — shape only; copy the real one from OneDesk
    https://<your-onedesk-host>/api/v1/t/<your-org>/itsm/email/oauth/callback/
    !

    Character-for-character, trailing slash includedA single wrong character is the most common cause of a failed connection.

  4. Add the permissions — delegated only

    Open Manage ▸ API permissions ▸ + Add a permission.

    Choose “APIs my organization uses”, search for Office 365 Exchange Online, open Delegated permissions, and tick:

    IMAP.AccessAsUser.AllSMTP.Send

    Then add Microsoft Graph ▸ Delegated permissions:

    offline_access

    Click “Grant admin consent” and confirm. Every row should now show Granted.

    !

    Do not tick anything under “Application permissions”Both permissions above appear in an Application variant as well. Choosing that variant is precisely the organisation-wide access model described in Section 0. Confirm the Type column reads Delegated on every row before you leave this page.

  5. Create the client secret

    Open Manage ▸ Certificates & secrets ▸ + New client secret. Choose an expiry of 6 to 12 months and copy the Value column immediately — Microsoft hides it as soon as you navigate away.

    i

    Set a calendar reminder nowA shorter expiry is deliberate: it forces regular rotation. When it lapses, mail ingestion stops and OneDesk shows a red “Can't send” badge on the mailbox. Set a reminder two weeks before the expiry date to issue a fresh secret and paste it in.

Section 4Lock down who can use the app

The most important step in this guide, and the one most setup instructions omit entirely.

Granting admin consent in Section 3 approved the permission for the whole directory. That does not hand the app anyone's mail — but without this step, any employee who reached the consent URL could complete a sign-in and connect their own mailbox. Restricting assignment closes that off.

  1. Require explicit assignment

    Go to Entra ▸ Enterprise applications ▸ your app ▸ Properties and set Assignment required? to Yes. Save.

  2. Assign the service account, and nobody else

    Open Users and groups ▸ + Add user/group and add only helpdesk-svc@yourcompany.com.

    ✓

    What you have just guaranteedExactly one account in your organisation can authenticate against this app, and that account can open exactly one mailbox. Anyone else attempting the sign-in is refused by Entra before a token is ever issued.

  3. Optional — Conditional Access on the service account

    Worth adding if your policy calls for it: restrict sign-in to expected countries, and keep your “block legacy authentication” policy switched on (OneDesk uses modern OAuth authentication and is unaffected by it).

    !

    Do not apply a short sign-in frequency policy to this accountOneDesk polls the mailbox unattended using a refresh token. A Conditional Access policy that forces frequent re-authentication will invalidate that token and break mail ingestion every few hours, with no obvious cause in the logs.

Section 5Connect the mailbox in OneDesk

Three values to paste, then one sign-in — where the single most consequential choice in this whole guide is made.

OneDesk screen
Settings ▸ Email ▸ Mailboxes ▸ Edit ▸ Connection tab

  1. Paste the three values

    Set Authentication to Microsoft 365 (OAuth2), then fill in the Client ID, Directory (tenant) ID and Client secret from Section 3. Set Username to the shared mailbox address, as explained in Section 1.

    ✓

    Always paste the real Directory (tenant) IDNever leave it blank and never enter common. The real value pins token issuance to your directory alone; common allows the sign-in endpoint to accept accounts from any Microsoft tenant.

  2. Save, then click “Reconnect mailbox”

    Microsoft shows an account picker. Sign in as helpdesk-svc@yourcompany.com.

    !

    Do not sign in with a Global Admin accountThis is the single decision that determines how much mail OneDesk can reach. The token OneDesk stores inherits whatever the signed-in account can open — so signing in as an administrator would hand it exactly the organisation-wide access this guide exists to prevent. If you are already signed into Microsoft as an admin in that browser, choose “Use another account”.

  3. Verify

    Click Test inbound connection. Then send a message to the support address and confirm it appears under Settings ▸ Email ▸ Email Log and becomes a ticket.

Section 6Standing controls

Four things to keep true after setup day.

!

Every message in the folder becomes a ticketOneDesk ingests everything it finds in the configured folder — there is no filter on who the message was addressed to. Never point it at a person's mailbox. If the support mailbox also receives mail that should not become tickets, create an Exchange inbox rule that files ticket mail into a subfolder, and set OneDesk's Folder field to that subfolder.

  • Enable mailbox auditing on the support mailbox and monitor the MailItemsAccessed action, so any access is attributable after the fact.
  • Review sign-in logs monthly — Entra ▸ Sign-in logs, filtered to this application. You should see the service account and nothing else.
  • Re-check the API permissions page whenever the app is modified, confirming the Type column still reads Delegated throughout.
  • Rotate the client secret before its expiry date, and delete the superseded secret afterwards.

Revocation runbook

Follow this when offboarding OneDesk, or immediately on any suspicion of compromise. Step 2 is the one that actually kills live access.

  1. Disconnect in OneDesk

    Settings ▸ Email ▸ Mailboxes — set the mailbox inactive. This stops polling.

  2. Revoke the token

    This invalidates the stored refresh token immediately:

    Revoke-MgUserSignInSession -UserId helpdesk-svc@yourcompany.com

  3. Delete the client secret

    Entra ▸ App registrations ▸ your app ▸ Certificates & secrets.

  4. Remove consent entirely

    Entra ▸ Enterprise applications ▸ your app ▸ Delete. Removing the service principal withdraws the granted permission from your directory.

  5. Remove the mailbox permission

    Remove-MailboxPermission -Identity support@yourcompany.com `
  -User helpdesk-svc@yourcompany.com -AccessRights FullAccess

ReferenceTerms used in this guide

Delegated permission
A permission the app exercises on behalf of a signed-in user. It can never reach more than that user can.
Application permission
A permission the app exercises as itself, with no user involved. For mail these are organisation-wide by default — the model this guide deliberately avoids.
Admin consent
An administrator approving a permission for the directory. For a delegated permission it makes sign-in possible; it does not by itself grant access to anyone's mail.
Assignment required
An Enterprise application setting that limits which accounts may authenticate against the app. The core control in Section 4.
Refresh token
A long-lived credential letting OneDesk obtain fresh access tokens without a person present — what makes unattended polling possible, and what step 2 of the revocation runbook destroys.
Shared mailbox
A mailbox with no licence and no sign-in of its own, accessed by delegates who have been granted permission to it.
XOAUTH2
The standard mechanism for presenting an OAuth token over IMAP or SMTP, in place of a password.
